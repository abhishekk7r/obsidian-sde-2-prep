# JVM Memory & Garbage Collection

## Quick Recap

> [!tip] Picture it
> - **Stack:** each thread's private notepad. One page per method call, page torn off when the method returns.
> - **Heap:** one shared warehouse. Every object sits here; the stack only holds the address slip.
> - **Metaspace:** the blueprint room. Class definitions, not objects.

| Question | Answer |
|---|---|
| Where do objects live | **Heap**, always (arrays too) |
| Where do local variables live | **Stack** frame: primitives by value, objects as a **reference** |
| Where do instance fields live | **Heap**, inside the object (even `int` fields) |
| Where do static fields live | **Heap**, with the `Class` object (Java 8+) |
| Where does class metadata live | **Metaspace** (native memory, not heap) |
| String pool | **Heap** since Java 7 |
| Shared vs per-thread | Heap + Metaspace shared. Stack + PC register per thread |

## Memory areas

```
 PER THREAD                         SHARED BY ALL THREADS
 ┌──────────────┐          ┌─────────────────────────────────────┐
 │ JVM stack    │          │ HEAP                                │
 │  frame: c()  │          │  ┌─────────────────────┬──────────┐ │
 │  frame: b()  │──refs──▶ │  │ YOUNG               │ OLD      │ │
 │  frame: a()  │          │  │ Eden │ S0 │ S1      │ (tenured)│ │
 ├──────────────┤          │  └─────────────────────┴──────────┘ │
 │ PC register  │          └─────────────────────────────────────┘
 ├──────────────┤          ┌─────────────────────────────────────┐
 │ native stack │          │ NATIVE MEMORY (outside the heap)    │
 └──────────────┘          │  Metaspace · code cache · direct    │
                           │  buffers · thread stacks            │
                           └─────────────────────────────────────┘
```

| Area | Holds | Sized by | Fails with |
|---|---|---|---|
| **Stack** | frames: local vars, operand stack, return address | `-Xss` (about 1 MB per thread) | `StackOverflowError` |
| **Heap** | all objects and arrays | `-Xms` / `-Xmx` | `OutOfMemoryError: Java heap space` |
| **Metaspace** | class metadata, method bytecode | `-XX:MaxMetaspaceSize` (unlimited by default) | `OutOfMemoryError: Metaspace` |
| **Code cache** | JIT-compiled native code | `-XX:ReservedCodeCacheSize` | JIT stops compiling, app slows |
| **Direct buffers** | off-heap NIO buffers (Netty, Kafka clients) | `-XX:MaxDirectMemorySize` | `OutOfMemoryError: Direct buffer memory` |

- **PermGen** = pre-Java-8 name for the class area, lived inside the heap with a fixed size. Replaced by Metaspace in Java 8

## Stack vs heap

```
 void pay() {
     int amount = 500;                 stack: amount = 500
     Account acc = new Account();      stack: acc = 0x7f1 ──▶ heap: Account{balance=0}
 }                                     frame popped → acc gone, object now garbage
```

| | Stack | Heap |
|---|---|---|
| Owner | one thread | all threads |
| Freed | automatically on method return | by GC, when unreachable |
| Speed | very fast (pointer bump) | slower (allocation + GC) |
| Thread safety | safe by design | needs synchronization |
| Size | small, fixed per thread | large, grows up to `-Xmx` |

> [!warning] Trap — "Java passes objects by reference"
> Java is **always pass-by-value**. For objects, the value copied is the **reference**. Method can mutate the object, but reassigning the parameter does not change the caller's variable.

> [!note] Escape analysis
> JIT may skip the heap for an object that never leaves its method (scalar replacement). "Objects always on heap" is the right interview answer; mention this only as a follow-up.

**Mnemonic:** *Stack holds the address slip, heap holds the parcel.*

## Inside the heap — generations

- **Why split:** most objects die young. Cleaning a small young area often is cheaper than scanning the whole heap

```
 new Object()
     │
     ▼
   EDEN ──(minor GC, still alive)──▶ S0 ⇄ S1 ──(age hits threshold)──▶ OLD
                                     age +1 per survived GC
```

- New object → **Eden** (each thread allocates from its own chunk, the **TLAB**, so no locking)
- Eden full → **minor GC**: live objects copied to a survivor space, age + 1, Eden wiped
- Survives enough minor GCs (threshold up to **15**) → promoted to **Old**
- Old full → **major / full GC**: slower, longer pause
- Very large objects may go straight to Old (G1: **humongous** regions)

> [!warning] Trap — premature promotion
> Survivor space too small → short-lived objects overflow into Old → Old fills quickly → frequent full GCs. Symptom: high GC time with a heap that looks "big enough".

## Errors and what they mean

| Error | Usual cause | First move |
|---|---|---|
| `StackOverflowError` | infinite / very deep recursion | fix recursion, then `-Xss` |
| `OOM: Java heap space` | leak, or heap genuinely too small | heap dump, find the dominator |
| `OOM: GC overhead limit exceeded` | GC running constantly, freeing almost nothing | same as heap space: it's a leak signal |
| `OOM: Metaspace` | too many classes loaded, classloader leak (redeploys, proxies) | cap + check dynamic class generation |
| `OOM: unable to create native thread` | too many threads, OS limit hit | thread pool, not thread-per-task |
| `OOM: Direct buffer memory` | off-heap buffers not released | check NIO / Netty usage |

- Always run prod with `-XX:+HeapDumpOnOutOfMemoryError`; open the dump in **Eclipse MAT**, look at the **dominator tree**

> [!danger] Trap — "Java has GC, so no memory leaks"
> Leak in Java = object **still reachable** but never used again. GC can't free what you still point to.

### Common leak sources
- `static` collection / cache with no eviction
- `ThreadLocal` in a thread pool, never `remove()`d — see [[3.9 ThreadLocal & BlockingQueue]]
- listeners / callbacks registered, never deregistered
- mutated key stuck in a `HashMap` — see [[2.2 HashMap & equals-hashCode]]
- unclosed streams / connections (use try-with-resources)

## Production case

- Pod **OOMKilled** by Kubernetes, but no `OutOfMemoryError` in logs and heap usage looked fine
- Why: container limit counts **total** process memory = heap + Metaspace + thread stacks + direct buffers + code cache. Heap was only part of it
- Fix: set `-XX:MaxRAMPercentage` (default max heap = **25%** of container memory) and leave headroom for non-heap; cap Metaspace and direct memory

> [!tip] Rule of thumb
> No `OutOfMemoryError` but the pod died → look **outside** the heap.

## Interview cards
- Q: `int x = 5` inside a method vs as a field? A: local → stack. Field → heap, inside the object
- Q: Stack vs heap, which is thread-safe? A: stack, one per thread. Heap is shared
- Q: PermGen vs Metaspace? A: PermGen in heap, fixed size. Metaspace in native memory, grows by default
- Q: Why generations? A: most objects die young, so collect the young area cheaply and often
- Q: 500 threads, memory cost? A: about 500 MB of stack reserved, outside the heap
- Q: How do you debug a heap OOM? A: heap dump → MAT → dominator tree → who holds the reference

**Mnemonic:** *Stack = per thread and automatic. Heap = shared and GC'd. Metaspace = classes. Killed without an OOM = non-heap.*
