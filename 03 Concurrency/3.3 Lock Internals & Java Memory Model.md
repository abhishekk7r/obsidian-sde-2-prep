# Lock Internals & Java Memory Model

## Quick Recap

> [!tip] Picture it
> - **Lock:** every object wears a name tag on its head (the **mark word**). Lock owner writes its name there.
> - **JMM:** each thread writes in its own notebook (CPU cache); main memory is the shared board. **Happens-before** = the rule that says when a notebook must be copied to the board.

| Question | Answer |
|---|---|
| Thin vs fat lock | **Same `synchronized` lock, two states.** Thin = owner written into mark word via CAS (no OS). Fat = mark word points to a **Monitor** with queues; waiters parked by OS |
| When thin → fat | A **second thread contends** (its CAS fails while owner is still inside) |
| Does `ReentrantLock` / `ReadWriteLock` use thin/fat? | **No** — they don't touch the mark word at all. Built on **AQS** (state int + CAS + queue) |
| `volatile done = true;` **then** `data = "ready";` — B sees `done`, reads `data` | **Not guaranteed.** Only writes made **before** the volatile write are carried |
| Memory barrier | A line in code that the CPU/JIT can't move reads/writes across + caches synced here |
| Who inserts barriers | `volatile` reads/writes, plus `synchronized` lock/unlock |

> [!danger] Trap — "the JMM guarantees it"
> Never answer this way. Name the exact happens-before rule and the chain (program order → volatile rule → program order). No chain = no guarantee.

> [!danger] Trap — thin lock for `synchronized`, fat lock for "read/write locks"
> Wrong. Thin and fat are both stages of the **same** `synchronized` monitor. Explicit locks are a separate mechanism (AQS).

## How `synchronized` works inside

```
 An object in heap memory
 ┌──────────────────────────────┐
 │ HEADER  (mark word)          │ ◀── lock info lives HERE
 │ class pointer                │
 ├──────────────────────────────┤
 │ fields: balance = 500 ...    │
 └──────────────────────────────┘
```

### Lock inflation

```
 UNLOCKED
    │  T1 enters, nobody else around
    ▼
 THIN LOCK      mark word = "T1 owns me"
    │           (CAS, no OS call → very cheap)
    │  T2 arrives while T1 still inside → T2's CAS fails
    ▼
 FAT LOCK (inflated)
    mark word ──▶ Monitor
                  ┌───────────────────────────┐
                  │ owner      : T1           │
                  │ entry queue: T2, T3       │ ◀ BLOCKED, waiting to enter
                  │ wait set   : T4           │ ◀ WAITING, called wait()
                  └───────────────────────────┘
```
- No contention → **thin** (cheap). Contention → **fat** (JVM decides, automatic)
- **Biased locking** — old optimisation, disabled/removed in modern Java; mention only if asked

### Bytecode

```
 synchronized (obj) { work(); }

   monitorenter obj
   work()
   monitorexit  obj          ◀ normal exit
   ── exception path ──
   monitorexit  obj          ◀ extra exit
   rethrow
```
- Extra `monitorexit` on the error path → `synchronized` **always** releases, even on exception

**Mnemonic:** *No fight = thin tag. Fight = fat monitor with a queue.*

## Java Memory Model & happens-before

```
     Thread A                 Thread B
   ┌──────────┐             ┌──────────┐
   │ notebook │ x = 42      │ notebook │ x = 0   ◀ old copy
   └────┬─────┘             └────┬─────┘
        │ copied to board?       │ re-read from board?
   ═════╧════════ MAIN MEMORY ═══╧══════════
```

- **Why:** CPU + JIT reorder code and cache values for speed → without rules, writes seen late, never, or out of order
- **JMM** = rules for **when** a write by one thread is guaranteed visible to another

### Happens-before rules

| Rule | Meaning |
|---|---|
| Program order | Earlier line → later line (same thread) |
| Monitor lock | `unlock(L)` → next `lock(L)` — **same lock only** |
| volatile | write to `v` → next read of `v` |
| Thread start | `t.start()` → everything inside `t` |
| Thread join | everything inside `t` → `t.join()` returns |
| Transitivity | A → B and B → C ⇒ A → C |

### Correct order — volatile "carries" earlier writes

```
 Thread A                         Thread B
 (1) data = "ready"
 (2) volatile done = true  ──hb──▶ (3) sees done == true
                                   (4) reads data → guaranteed "ready"
 (1)→(2) program order · (2)→(3) volatile · (3)→(4) program order
```

### Wrong order — no guarantee

```
 Thread A                         Thread B
 (1) volatile done = true  ──hb──▶ (3) sees done == true
 (2) data = "ready"                (4) reads data → may be null ✘
 (2) comes AFTER the volatile write → no path from (2) to (4)
```

> [!tip] Picture it
> The volatile write is sealing a parcel. Everything packed **before** sealing arrives. Something you drop in **after** sealing isn't promised to arrive.

> [!warning] Rule for code
> Write the data first, set the volatile flag **last**. Read the flag **first**, then the data.

## Memory barriers (how `volatile` is implemented)

```
   normal writes  (data = "ready")
 ════════ BARRIER ════════   ◀ writes above can't move below
   volatile write (done = true)
              ...
   volatile read  (done)
 ════════ BARRIER ════════   ◀ reads below can't move above
   normal reads   (data)
```
- **Barrier / fence** = line the CPU/JIT may not reorder reads/writes across; caches synced at that point
- Inserted by `volatile` read/write and `synchronized` enter/exit

### Production case
- Config-reload thread sets `config = newConfig` → request threads keep old config for minutes
- Fix: `volatile` reference, or publish under a lock

**Mnemonic:** *Unlock → lock, volatile write → read, start → run, run → join. Data first, flag last.*
