# Atomics & Concurrent Collections

## Atomic Classes & CAS

### Quick Recap

> [!tip] Picture it
> A shared whiteboard showing 5. "Change it to 6 **only if it's still 5**." Someone changed it first → re-read, try again. Nobody locks the board.

```
 loop:
    old = read value          (5)
    new = old + 1             (6)
    CAS(expected=5, new=6)
       ✔ still 5 → set 6, done
       ✘ changed  → back to loop   (thread NOT parked)
```
- CAS = **one CPU instruction** (`cmpxchg` on x86) — compare + swap can't be split

| Question | Answer |
|---|---|
| Why is `incrementAndGet()` safe but `volatile count++` isn't? | volatile = fresh reads only; `++` is still 3 steps. Atomic does read-add-write as one step via the CAS retry loop |
| When is CAS slower than a lock? | Heavy contention → threads keep failing + retrying, burning CPU. Lock parks them instead |
| Counter hit by 100 threads, read once a minute | **`LongAdder`** — spreads writes over cells, `sum()` on read |
| ABA | Value A → B → A; CAS sees A, thinks nothing changed. Fix: `AtomicStampedReference` (version bumps on **every** change) |
| Update `balance` + `txCount` together | CAS = one variable only → immutable object + `AtomicReference`, or a lock |

> [!danger] Trap — "volatile is enough for a hot counter"
> No. volatile `count++` from 100 threads loses updates. A lock is correct but slow under that contention. `LongAdder` is the answer.

---

![[cas-retry-loop.svg]]

- **CAS** — atomic CPU instruction: read → compare to expected → swap if match, else no-op. Never blocks; failure just retries
- "Lock-free" = thread stays runnable on failure, just loops — never parked like a blocked lock-waiter

**`volatile` vs `AtomicInteger`:**

| | `volatile int` | `AtomicInteger` |
|---|---|---|
| Guarantees | Visibility only | Visibility + atomicity |
| Safe `i++`? | No | Yes (CAS loop) |

- `compareAndSet(expected, new)` → returns `true`/`false`; manual retry = `while(!cas(current, current+1)) current = get();`

> [!warning] CAS ≠ always faster than locking
> Extreme contention → repeated failed retries burn CPU + bounce cache lines. Locks park failed threads (no CPU cost while waiting). Low/moderate contention → CAS wins clearly.

![[longadder-striping.svg]]

- `LongAdder` stripes a hot counter across cells, one per thread bucket — `sum()` aggregates on read
- Use for write-heavy/read-rarely counters (metrics); use `AtomicLong` when you need a precise value on every read

> [!danger] ABA problem
> CAS can't detect A → B → A — looks unchanged, but structure moved underneath. **Fix:** `AtomicStampedReference` — CASes on `(value, stamp)` pair, stamp increments on every update so a return-to-A is still caught. (`AtomicMarkableReference` = lighter boolean-mark variant.)

> [!warning] CAS = one memory location, never several at once
> Need `balance` + `transactionCount` atomic together? Wrap both in one immutable object and CAS the *reference*, or fall back to a lock.

> [!tip] Mnemonic
> One CAS, one location. Lock-free ≠ always faster. Stripe hot counters.

## Concurrent Collections

### Quick Recap

> [!tip] Picture it
> - `HashMap` = shared cupboard, no lock
> - `synchronizedMap` = one lock on the whole cupboard
> - `ConcurrentHashMap` = a lock on **each shelf**
> - `CopyOnWriteArrayList` = printed notice; to change it, print a full new copy and swap it

```
   T1 put(→b0)    T2 put(→b2)    T3 put(→b2)    T4 get(→b4)
       ▼              ▼              ▼              ▼
 ┌──────────┬─────┬──────────┬─────┬──────────┬─────┐
 │ b0 empty │ b1  │ b2 🔒 T2 │ b3  │ b4       │ b5  │
 └────┬─────┴─────┴────┬─────┴─────┴────┬─────┴─────┘
  CAS insert,     lock ONLY b2,     read, no lock
  no lock         T3 waits
  → T1, T2, T4 run together. Only T3 waits.
```

| Question | Answer |
|---|---|
| Why no `null` in CHM? | `get(k) == null` must mean only "not present". If null were allowed it could also mean "stored null", and with many threads you can't safely re-check with `containsKey` (map may change in between) |
| `if (!containsKey(k)) put(k, createExpensive())` from 10 threads | Several threads pass the check → **expensive object built many times**, later `put` overwrites earlier one → threads may hold different instances |
| Fix | `map.computeIfAbsent(k, x -> createExpensive())` — built **exactly once** |
| Listener list, read every event, changed once a day | **`CopyOnWriteArrayList`** — lock-free reads, rare O(n) copy is fine |
| Same list changed 1000×/sec | Not COW (copies whole array every write) → `ConcurrentHashMap.newKeySet()` or `ConcurrentLinkedQueue` |

> [!danger] Trap — `putIfAbsent(k, createExpensive())` is not the same fix
> Java evaluates the argument **before** the call → `createExpensive()` still runs in all 10 threads; only one result is stored. `computeIfAbsent` takes a function, so it runs only when the key is missing.

> [!danger] Trap — modifying the same map inside `computeIfAbsent`
> Function runs while the bucket is locked → recursive memo (e.g. Fibonacci) → `IllegalStateException` or hang. Keep the function short, no same-map writes.

> [!warning] `LongAdder` is a counter, not a collection
> Don't mix it up with list choices.

**Mnemonic:** *Shelf locks, not cupboard lock. No nulls. Check-then-act → computeIfAbsent (function, not value). COW: writers pay, readers fly.*

---

![[chm-vs-synchronizedmap-locking.svg]]

- **CHM:** thread safety via bucket-level locking, not one global lock
- **Java 8 rewrite:** pre-8 = fixed 16 `Segment`s (own lock each, capped concurrency). Java 8 = per-bin locking + CAS on empty bins + treeification (>8 collisions → red-black tree, O(log n) worst case)
- **Iteration:** weakly consistent — never throws CME (unlike `HashMap`'s fail-fast iterator)

> [!warning] `size()` is an estimate, not exact
> Sums per-bucket counts that can still be changing mid-call — no lock, no copy taken.

> [!tip] `putIfAbsent()` is atomic
> Only one thread ever inserts for a given key. Losers get the existing value back — never overwrite.

![[copy-on-write-mechanism.svg]]

- **`CopyOnWriteArrayList`:** every write copies the whole array, then atomically swaps the reference
- Reads are lock-free (just read current reference); iterators are bound to the array snapshot at creation — never see later writes, never throw CME

| | Cost |
|---|---|
| Reads | Fast, lock-free |
| Writes | O(n) — full copy every time |

> [!tip] Mnemonic
> Copy-On-Write: writers pay so readers never have to. Good for read-heavy/write-rare; bad for write-heavy.

#### vs `Collections.synchronizedX(...)`

| | `synchronizedMap`/`synchronizedList` | CHM / COW |
|---|---|---|
| Locking | Whole collection, every op | Fine-grained or none |
| Consistency | Strong | Weakly consistent / snapshot |
| Best for | Need strict read+write consistency together | High-concurrency reads or scale-out writes |
